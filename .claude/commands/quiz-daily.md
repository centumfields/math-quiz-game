수학 연산 퀴즈의 문제은행을 아래 7단계로 점검하고 필요하면 새 문제를 보충해 주세요. 인자가 있으면 참고하세요: $ARGUMENTS

인자 예: `target=25` (카테고리당 목표 문항 수). 인자가 없으면 목표는 현재 규칙(카테고리당 20문항, 난이도 하/중/상 = 7/8/5, 정답 위치 A–D 각 5개)입니다.

## 공통 규칙 (모든 단계에 적용)

- **단계마다 검증하고, 검증에 실패하면 그 자리에서 즉시 중단합니다.** 다음 단계로 넘어가지 말고, 실패한 단계 번호·실행한 명령·기대값과 실제 값·오류 출력 원문을 그대로 보고합니다. 임의로 우회하거나 재시도 루프를 돌리지 않습니다.
- 중단 시점에 이미 파일을 바꿨다면(5단계) 단계 5의 **롤백**을 먼저 수행한 뒤 보고합니다. 롤백한 사실과 결과도 보고에 포함합니다.
- `python`은 스토어 스텁일 수 있으므로 `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`를 씁니다. Node는 없습니다. 임시 스크립트와 스냅샷은 스크래치패드에 두고 프로젝트에는 두지 않습니다(6단계 백업만 예외).
- `questions.js`는 **직접 수정하지 않습니다.** 문제 추가는 `gen_questions.py`를 고치고 재생성해서만 합니다.
- 파일이 UTF-8이고 마이너스는 `−`(U+2212)이므로, 출력이 깨져 보이면 `PYTHONIOENCODING=utf-8`로 실행합니다.

## 1. 퀴즈 파일 구조 읽기·이해

1. `questions.js`, `gen_questions.py`, `validate_questions.py`, `CLAUDE.md`의 "Architecture" 절을 읽습니다.
2. 다음을 확인해 한두 줄씩 정리합니다.
   - `window.QUESTIONS = [...]` 형태와 문항 필드(`id`, `area`, `op`, `category`, `level`, `question`, `choices`, `answerIndex`, `explanation`, `concept`).
   - 영역(nat/int/rat) × 연산(add/sub/mul/div) = 12개 카테고리, `id`가 1부터 연속인지.
   - 생성기의 `SEED`, `LEVELS`, 카테고리별 생성 함수, 검증기가 하드코딩한 기대값(문항 수·난이도·정답 위치).
3. **검증:** `questions.js`를 `window.QUESTIONS = ` 뒤의 JSON으로 파싱할 수 있어야 하고, 위 필드가 모든 문항에 있어야 합니다. 파싱 실패나 필드 누락이면 즉시 중단합니다.

## 2. 현재 문제 개수와 분포 확인

스크래치패드에 일회용 스크립트를 만들어 `questions.js`를 읽기 전용으로 집계합니다.

- 전체 문항 수, 카테고리별 문항 수, 카테고리별 난이도 하/중/상, 카테고리별 정답 위치 A–D.
- 기준 상태를 확인하기 위해 `python validate_questions.py`도 실행합니다.
- **검증:** `validate_questions.py` 종료 코드가 0이어야 합니다. 1이면 이미 데이터가 깨진 상태이므로 중단하고 실패한 검사 항목을 그대로 보고합니다. (추가 작업은 정상 상태에서만 시작합니다.)

## 3. 카테고리별 부족한 부분 파악

목표(인자 `target`, 없으면 현재 규칙)와 2단계 집계를 비교해 카테고리마다 부족분을 표로 만듭니다.

| 카테고리 | 현재 | 목표 | 부족 문항 | 부족 난이도(하/중/상) | 부족 정답 위치 |
|---|---|---|---|---|---|

- 목표 난이도 비율은 7/8/5(합 20)를 목표 문항 수에 비례해 배분하고, 정답 위치는 4개가 고르게 나뉘도록 합니다. 나누어떨어지지 않으면 어떻게 배분했는지 적습니다.
- **분기:**
  - 모든 카테고리가 목표를 충족하면 "추가할 문항 없음"을 기록하고 **4·5단계를 건너뜁니다.** 이는 실패가 아니라 정상 종료이며 6·7단계는 그대로 진행합니다.
  - 목표가 현재 규칙(카테고리당 20문항, 7/8/5)과 다르면 검증기·`CLAUDE.md`의 기대값·`id` 규칙을 함께 바꿔야 합니다. 이 경우 **여기서 멈추고 사용자에게 확인을 받습니다.** 인자에 `approve=1`이 있으면 확인된 것으로 보고 진행합니다.
- **검증:** 부족분의 합이 (목표 총 문항 수 − 현재 총 문항 수)와 같아야 합니다. 어긋나면 중단합니다.

## 4. 새 문제 추가 전 중복 체크

추가 후보를 정하기 **전에** 기준 데이터를 점검합니다.

- 기존 240문항의 `question` 텍스트 중복(완전 일치), 교환법칙으로 같은 문항(예: `3 + 5`와 `5 + 3`)인 덧셈·곱셈 쌍, 같은 카테고리 안에서 같은 피연산자 쌍이 다른 난이도에 들어간 경우를 찾습니다.
- 이후 5단계에서 생성한 새 문항은 기존 문항과 같은 기준으로 비교합니다(`question` 완전 일치 금지, 같은 카테고리 내 교환법칙 중복 금지).
- **검증:** 기존 데이터에 완전 중복이 있으면 중단하고 중복 문항 `id`를 보고합니다. 교환법칙 중복은 목록만 보고하고(이미 있던 것이면 경고), 새로 늘어나서는 안 됩니다.

## 5. 문제 추가 후 형식 검증

1. **스냅샷:** 변경 전에 `questions.js`와 `gen_questions.py`를 스크래치패드로 복사하고 SHA-256을 기록합니다(롤백용).
2. **추가:** `gen_questions.py`에서 부족한 카테고리·난이도의 문항을 만들도록 수정합니다. 기존 문항의 `id`·내용이 바뀌지 않도록(고정 `SEED`의 기존 결과 보존) 주의하고, 바뀌면 그 사실을 보고에 적습니다. 그 뒤 `python gen_questions.py`로 재생성합니다.
3. **검증 (모두 통과해야 함):**
   - `python validate_questions.py` 종료 코드 0.
   - 독립 재계산: 모든 문항의 `question`을 직접 파싱해 `fractions.Fraction`으로 계산하고 `choices[answerIndex]`와 대조(보기 중복 없음, 정답 위치 분포, 유리수 기약분수, `−`는 U+2212, 해설의 최종값 일치).
   - 4단계 기준으로 새 문항의 중복 없음.
   - 카테고리별 문항 수·난이도·정답 위치가 목표와 일치, `id`가 1..N 연속.
4. **롤백:** 위 검증이 하나라도 실패하면 즉시 중단하고, 스냅샷으로 `questions.js`와 `gen_questions.py`를 되돌린 뒤 SHA-256이 스냅샷과 같은지 확인합니다. 그리고 실패 내용과 롤백 결과를 보고합니다.
5. **성공 시 마무리:** `questions.js`가 바뀌었으므로 `sw.js`의 `VERSION`과 `app.js`의 `APP_VERSION`을 **같은 값으로 올립니다.** `validate_questions.py`·`CLAUDE.md`의 기대값이 달라졌다면 함께 고치고, `test.html`로 단위 테스트가 모두 통과하는지 확인합니다(헤드리스 Edge, 하네스는 프로젝트 밖).

## 6. 전체 데이터 백업

- 프로젝트 폴더의 `backups/<YYYYMMDD-HHMMSS>/` 아래에 `questions.js`, `gen_questions.py`, `validate_questions.py`를 복사합니다. 추가 작업이 없었어도 현재 상태를 백업합니다.
- **검증:** 복사본마다 원본과 SHA-256이 같아야 하고, 백업한 `questions.js`가 다시 파싱되어 문항 수가 일치해야 합니다. 기존 백업 폴더는 덮어쓰거나 지우지 않습니다. 실패하면 중단하고 보고합니다.
- `backups/`는 앱 파일이 아니므로 `ASSETS`에 넣지 않습니다.
